# TriageCopilot — Round 2 Prototype

**Accenture Innovation Challenge 2026 · Team shourya56777 · Problem Track 2: PatientTriage.ai**

TriageCopilot is a decision-support layer for emergency department triage. It suggests an
ESI-style acuity score (1 = most urgent, 5 = least urgent) with a plain-language reason and
an explicit confidence value — it never sets the final score, and it never returns a bare
number without that confidence. This repository is the working prototype for Round 2: the
scoring mechanism, a simulated patient set, a 3x surge test, a waiting-room deterioration
recheck, a clinician override, and a full audit log, all runnable locally.

## What it decides vs. what it recommends (the core design call)

| | |
|---|---|
| **Recommends only** | ESI-style acuity score + reason, at check-in and on every recheck. A nurse must sign off — no exceptions. |
| **Acts on its own** | Exactly one thing: pushing a red-flag pattern (stroke, MI, sepsis) straight to a clinician immediately. |

Everything else — the actual acuity a patient is assigned — is a human call.

## Why this design, in one line

Under-triage and over-triage are not equally costly. Missing a critical case is categorically
worse than over-prioritizing a minor one, so every uncertain read is designed to fail toward
*more* cautious, never less.

## Running it

No installs required — pure Python standard library, no `pip install` needed.

```bash
# 1. Run the simulation (regenerates output/simulation_output.json)
cd src
python3 simulate.py

# 2. Serve the project root so the dashboard can fetch the output file
cd ..
python3 -m http.server 8000

# 3. Open the dashboard
# http://localhost:8000/docs/dashboard.html
```

> The dashboard uses `fetch()` to load `output/simulation_output.json`, which browsers block
> for files opened directly (`file://...`) as a security measure — you must serve the folder
> over HTTP, not double-click `dashboard.html`. This also means it's ready to publish as-is
> via **GitHub Pages** (point Pages at the repo root or `/docs`).

## Assumed regulatory jurisdiction

This prototype assumes a **US hospital operating under HIPAA**. That choice shapes three
design commitments made explicit in the audit log:

1. **Every AI suggestion and every human override is retained together**, not just the final
   value — HIPAA's audit-control requirement (§164.312(b)) expects the ability to reconstruct
   who changed what, and why.
2. **The AI never stores or transmits PHI beyond what's needed for the current triage decision**
   — no patient data leaves the scoring layer for model retraining without a separate, explicit
   consent and de-identification step (see Business Proposal, Data Protection section).
3. **Overrides require a documented reason**, not just a new number, so the record satisfies
   both clinical and legal review.

## Known limitations (stated honestly, per the brief's "no single correct architecture")

- **Two age bands for scoring, but the pediatric norms shown are illustrative,** not a real
  age-in-months clinical reference. A production system would need continuous, age-in-months
  lookup tables (e.g., PALS ranges), not three flat bands.
- **The complaint-severity lexicon is a small, hand-built dictionary** (`COMPLAINT_WEIGHTS` in
  `engine.py`), not an NLP model. It's intentionally simple so the *decision logic* is fully
  auditable; a real deployment would need a much larger, clinically validated symptom
  vocabulary, likely with a retrieval step against a maintained clinical ontology.
- **`P020` (age 15) is scored as an adult** under the current two-cutoff age-banding
  (pediatric < 12, geriatric ≥ 65). This is flagged deliberately in the data file as a known
  gap — adolescent vitals sit in an awkward zone between pediatric and adult norms, and a real
  system needs a proper adolescent band rather than defaulting to adult.
- **The surge simulation uses an illustrative wait-time model** (`avg_minutes_between_checks`
  scales linearly with the arrival multiplier), not a real queueing simulation. It's built to
  demonstrate the *mechanism* — recheck thresholds catching at-risk patients under load — not
  to produce a validated capacity model.
- **Fall risk with normal vitals can under-score.** `P007` (71-year-old, dizziness and a fall,
  fully normal vitals) scores ESI 5 in this prototype, which understates real fall-risk
  concern in geriatric patients. This is a known gap in the complaint lexicon rather than a
  vitals-model issue, and is exactly the kind of case a real clinical advisory board review
  would need to catch before deployment.
